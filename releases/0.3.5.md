No schema change, no migration step. After `mw update`, run `mw update --plugins` once if you upgrade from 0.3.2 or 0.3.3.

Ceremonies (TSK-024 to TSK-027)

- New job keys `ceremonies` (any of `review`, `planning`, `triage`, `spike`; unknown names are refused) and `ready_min` (1..20, default 3) in `mw jobs set` and `mw jobs show`. A job without them prints exactly as before. No new commands.
- The dispatcher prompt gets a Ceremonies section, for the listed names only: triggers, dedupe by title, one ceremony session at a time, a daily cap, triage, the hotfix lane, a release ask, hands off `doing` items.
- The session prompt has role blocks `review`, `planner` and `spike` (output folders, at most one `mw ask`, screenshots only). A block now renders only when the session's job lists the matching ceremony (`review`, `planning`, `spike`). Before this fix every `-a review` session got the review block, whatever its job listed.
- USAGE and PROTOCOL describe ceremonies and which protocol steps stay with a human (`merge`, push, tag). Prompts are never read from repo files.

Alerts

- `mw log --follow [--since CURSOR|start] [--poll SEC] [--exec]` is a live feed of board events (TSK-035). With `--exec` it runs your `alerts.exec` for each event whose action is in `alerts.on`: an argv array, never a shell, the event as a JSON temp file appended as the last argument, stdin closed, 30 s.
- The command also gets 5 s to release its pipes after it ends or is killed, so a child that keeps them open cannot hang the feed.
- On Windows a `.bat` or `.cmd` `alerts.exec` runs through `cmd.exe`, so its arguments get cmd parsing. Use an `.exe` or `pwsh -File` for exact argv.
- A feed that starts from now retries its first read a few times when the board is mid-write.
- Each followed tenant has its own cursor: a tenant that is archived and restored while the feed runs does not replay its history. With `-A` the tenant list is fixed when the feed starts.
- `mw jobs show -j` carries `news_path`, the confined real path of the desk's `status.md` (empty when it does not resolve, for `../` or a symlink out of the workspace) (TSK-030).

Kit

- `buildlock.sh` and `buildlock.ps1` (TSK-031): the PowerShell lock is published by one atomic rename, so two waiters cannot both take it, and a test runs it under pwsh on all three CI systems (wait, timeout 75, exit code passthrough, stale takeover, flags, four-waiter takeover).
- A lock folder with no pid file that is older than about a minute counts as stale and is taken over through the same takeover path. A younger one is never taken, because a live owner writes its pid within milliseconds.

Fanfare

- A board written before 0.3.4 that stores `enabled: false` for "never set" cannot be told from an explicit off, so it is left alone; `mw fanfare` (and `-j`, key `hint`) now prints `board says off; mw fanfare set enabled=true to follow your setting` when such an off silences a user who turned fanfare on (TSK-058).
- `scripts/gen_fanfare_default.py` is libm-free, so the built-in fanfare WAV is byte-identical on Linux, macOS and Windows; CI compares its sha256 on all three (TSK-061).

mw-jobs plugin

- The news file button opens the path from `jobs show -j` `news_path`, only when it is a regular file (not a symlink) ending in `.md` or `.html`: `open -t` on macOS, `notepad.exe` on Windows, `xdg-open` on Linux, argv only. The plugin reads no `HOME` and no `summary` or news file of its own (TSK-033).
- Alerts of kind `review` fire without a model too, and `metrics` alerts on any change of a `metrics.json` row (`Metrics change:`; `Metrics drop:` for a drop) (TSK-060).
- `mw_panes_open` right after a plugin install no longer hangs on a cold `mw boards` scan: it waits 5 s, then answers "still looking, call again". Not verified in a live Claude session right after install (TSK-063).
- A guard test and `scripts/check-mw-jobs-no-notify.sh` make sure the plugin never raises an OS notification banner; alerts stay a toast plus a ping (TSK-064).
